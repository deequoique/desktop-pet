# 评估 TRTC 游戏共享迁移

## Goal

评估使用腾讯云实时音视频（TRTC）替换或补充当前 P2P + 单节点 coturn 媒体链路的可行性、改造边界和持续成本，使中国大陆与新加坡等跨区域场景下的游戏画面与系统声音更稳定。

本任务先产出决策所需的方案和成本模型；2026-08-14 用户进一步明确要求把 TRTC 结合进现有项目，因此范围扩展为实现可回滚的最小混合接入。

## Background

- 当前主媒体 PeerConnection 同时承载游戏画面、系统声音和可选麦克风。
- 2026-08-12 诊断中，同一网络环境下摄像头 P2P 链路约 133–145ms，但主媒体链路在 TURN/TCP、TURN/UDP 与 IPv4 P2P 之间波动，出现 330–914ms RTT、最高 87.5% 丢包和 ICE 失败。
- 用户主要共享游戏，屏幕分享保底必须达到 30fps；固定 10fps、15fps 或弱网降至低于 30fps 的方案已明确排除。
- 当前应用由 Electron pet、React control、Node/Socket.IO server 组成，没有第三方 RTC SDK 依赖。
- 修复前的 camera PC 会在主连接成功且选路明确后自动预热，即使双方摄像头均关闭；关闭摄像头虽不持续发送视频帧，但仍保留 ICE/STUN 心跳、候选探测和可能的 TURN allocation。该行为已由本任务的独立前置修复移除。

## Requirements

### R1. 游戏体验硬约束

- 游戏画面发送帧率不得低于 30fps。
- 系统声音是游戏共享的核心媒体，麦克风是可选媒体。
- 方案必须说明在 30fps 硬约束下如何通过区域接入、云端转发、码率/分辨率调整或弱网恢复改善稳定性。

### R2. TRTC 架构方案

- 说明 TRTC 应完全替换当前 WebRTC 媒体层，还是作为跨区域失败时的回退链路。
- 保留 Socket.IO 的房间、设备、控制和业务信令职责，明确哪些 RTC 信令交由 TRTC。
- 覆盖 Electron pet、控制端、游戏屏幕、系统声音、双方可选麦克风和摄像头。
- 说明鉴权、UserSig 签发、房间映射、媒体状态、诊断、灰度、回滚和供应商故障降级边界。

### R3. 成本模型

- 只使用腾讯当前官方价格和计费规则，注明查询日期、币种、地域或站点差异、免费额度与套餐限制。
- 至少估算以下场景：
  - 游戏画面 + 系统声音，双方麦克风关闭，摄像头关闭；
  - 游戏画面 + 系统声音 + 双方麦克风；
  - 游戏画面 + 系统声音 + 双方摄像头和麦克风。
- 对每个场景给出每小时、100 小时/月、500 小时/月和 1000 小时/月的成本。
- 区分 720p30 与 1080p30；若 TRTC 按接收分辨率计费，明确每个订阅者和每路流的计费乘数。
- 单列当前 coturn 服务器、出口带宽或跨境流量等不能从仓库确定的成本，不伪造比较数字。
- 首选入门版按量付费；“弱网通话卡顿优化”不得成为默认生产依赖，只有标准 TRTC 对照失败且增值版实测显著改善时才考虑购买。

### R4. 决策输出

- 给出 TRTC 迁移收益、改造成本、运行成本、供应商锁定和数据/合规风险。
- 给出推荐的最小验证版本及成功/停止条件。
- 不把 TRTC 的官方营销指标当作本项目实测保证；正式迁移前必须完成大陆与新加坡真实双端验证。

### R5. 摄像头按需建链

- 取消当前 camera PC 自动预热；通话建立后，只要双方都没有明确打开摄像头，就不创建 camera transport。
- 首次打开任一方摄像头时再创建 camera PeerConnection；用户接受首次开启需要额外等待一次 ICE 建链和首帧。
- 摄像头关闭时继续停止 capture 并移除 sender track，不能在关闭状态发送视频 RTP。
- 双方摄像头都关闭后立即销毁 camera transport，不保留快速重开的宽限期；再次打开时重新建链。
- 若后续把摄像头迁到 TRTC，也必须沿用按需进房/发布原则，不能因预热产生无效在房时长或额外身份计费。

## Acceptance Criteria

- [ ] 官方计费规则可追溯，所有计算公式与假设明确。
- [ ] 720p30、1080p30 的三种媒体组合均有小时/月度成本表。
- [ ] 架构方案覆盖当前 Electron、Web、server 三个运行时和现有功能。
- [ ] 最小验证版本保留至少 30fps 游戏共享和系统声音。
- [ ] 明确 POC 成功门槛、预算止损点、灰度与回滚方式。
- [ ] 先完成入门版标准 TRTC 测试，再以完全相同条件测试限时增值体验，能够用数据判断是否需要弱网套餐。
- [x] 从通话建立到首次明确打开摄像头之前，不创建 camera PeerConnection、不进行 camera ICE/TURN 探测，也不产生 camera TRTC 在房用量。
- [x] 双方摄像头关闭后立即释放 camera PeerConnection、ICE/TURN 状态与相关计时器；重新打开能够重新建链并恢复出画。
- [x] 用户审核并选择进入 TRTC POC；先执行官方 Electron SDK 无代码/隔离验证，再决定是否接入业务仓库。
- [ ] TRTC 已通过现有 Electron preload 安全桥接接入内置控制窗口，不开启 renderer `nodeIntegration`。
- [ ] Server 能为当前 call 和当前 controller 签发短期 UserSig；SDKSecretKey 只存在于 server 环境变量。
- [ ] `TRTC_MEDIA_MODE=trtc` 时，目标设备发布至少 30fps 的屏幕与系统声音，发起设备订阅并渲染；`webrtc` 模式可原样回滚。
- [ ] 摄像头仍走现有按需 WebRTC，不因 TRTC 主媒体接入重新引入空闲 camera transport。

## Out of Scope

- 固定或自适应降至 30fps 以下。
- 购买腾讯云套餐或直接修改线上服务器环境变量。
- 本任务中删除当前 WebRTC/coturn 实现。
- 在实测前承诺 TRTC 必然解决所有跨区域网络问题。
